1. 一分钟概览（含三问三答）

OpenSpec 是 AI 编码代理的规格治理层：它不写代码、不调模型，只管「变更该怎么被提议、评审、合并进规格真相」。四个记住就入门的不变量：

  • specs 是真相，changes 是提案——所有工作以 change 为单位，归档时增量合并进主规格；
  • CLI 是引擎，命令/技能是方向盘——规则只写一份（CLI + schema），30+ 种 AI 工具只做格式适配；
  • 纯本地、零内容外发——所有工件是本地文件，唯一的常规外发是可关闭的匿名遥测（命令名+版本）；
  • 治理面可插拔——schema 可定义新工件与规则；experience-loop 扩展（本工作树新增）示范了经验闭环：change 收尾 retro → 人审沉淀入经验库 → 下次 propose 检索注入 → lint 执法/度量。
怎么用

终端跑 openspec init 装触发文件 → 在 AI 聊天里敲 /opsx:propose 写提案 → /opsx:apply 实现 → /opsx:archive 归档合并。全部日常操作发生在 AI 聊天框，终端只管安装与校验。

深挖三问三答

① 触发机制：双通道「命令文件」与「技能文件」，三工具各取所需

OpenSpec 不常驻、无守护进程。它由 openspec init/update 把两类文件写进各 AI 工具的约定目录：slash 命令文件（per-tool 格式）与 SKILL.md 技能文件（Agent Skills 跨工具标准）。触发分两处：用户显式（敲 /opsx:*、$openspec-*）与模型自动（harness 按 SKILL.md 的 description 匹配选用）。Claude Code 双通道（/opsx:<id> 目录命名空间 + 技能）；Codex 单通道 skills-only（$openspec-<skill>，无命令文件）；OpenCode 双通道（/opsx-<id> 文件名扁平 + 技能，正文注入 $ARGUMENTS）。详见 §4。

② 经验总结：核心部分存在——有「经验注入」接口，无「经验自动总结」（扩展已补）

核心 OpenSpec 有把人类经验喂给每次运行的正式通道：config.yaml 的 context（必读）与 operations.*.guidance（择宜遵循，不遵循须说明），每次 instructions 新鲜读出；探索期有「洞察捕获」表。但这些都由人手写，核心无自动回顾（retro）/教训回写。experience-loop 扩展补上了 retro 工件与经验库。详见 §9 与 §11。

③ 循环沉淀：存在——但沉淀「行为真相」（specs），非「过程经验」（扩展已补经验）

核心循环 explore→propose→apply→verify→sync→archive 本身就是沉淀流水线：每次 change 的 delta specs（ADDED/MODIFIED/REMOVED/RENAMED）归档时合并进 openspec/specs/，成为下一轮基线；change 本体移入 changes/archive/ 留档。但沉淀粒度是规格而非教训——核心无 retro、无经验库、无自动回写（experience-loop 扩展补上）。详见 §10。

2. 系统任务边界：一个引擎，两顶帽子（图 1）

这张图回答：系统分成哪两半、三工具各自落在哪、终端与聊天如何分工。

机制先行：OpenSpec 是「规格驱动开发」的治理层，不是聊天助手也不是编码代理。它约束 AI 编码代理的工作流程与产物，而非替它写代码。进来什么：用户意图 + openspec/ 下已有规格/change 工件/配置；出去什么：结构化变更工件、实现后代码（AI 产出）、归档合并的 delta、留档历史；谁判定成败：人（评审/验收）+ validate 结构校验 + verify 一致性核查；主复杂度在跨工具适配（30+ 工具格式）与工件依赖治理（schema 工件图、增量合并语义）。

为什么值得这样切分

docs/how-commands-work.md 的比喻准确：CLI 是「引擎」（懂规则：change 目录形状、工件依赖、delta 合并），slash 命令是「方向盘」（每种工具长得不一样）。openspec init 在终端跑一次把方向盘装进所选 AI 工具；之后日常驾驶都在 AI 聊天框。

新人提示

想找「某个行为为什么是这样」：先去 src/core/ 对应模块（规则），再看 schemas/spec-driven/schema.yaml（工作流说什么），最后看 skills/（代理被教导怎么做）——三层同一件事的三个侧面。想加治理规则而不改核心，照 extensions/experience-loop/ 的样子做。

4. 触发机制：init 装了什么、三工具如何被触发（图 3-5）

本节回答：OpenSpec 在 Claude Code / Codex / OpenCode 里如何被触发——init 安装了什么、三工具的入口拼写/路径差异、技能内部的防骚扰守卫。

4.1 init 做了三件事

  1. 探测工具：按目录特征（detectionPaths）识别项目在用哪些 AI 工具——.claude/→Claude Code，.agents/skills 或 .codex/skills→Codex，.opencode/→OpenCode；也可 --tools claude,codex,opencode 显式指定。
  2. 生成两类触发文件：命令（commands）——per-tool 的 slash 命令 prompt 文件，由 src/core/command-generation/adapters/ 下 30+ 适配器各写各的格式（路径/frontmatter/参数占位都不同）；技能（skills）——openspec-*/SKILL.md，Agent Skills 标准，跨工具共用一份内容，仅个别字段按工具裁剪。12 个技能对应 12 条可安装工作流（propose/apply/archive/explore/verify/onboard…）。
  3. 登记调用拼写：命令「怎么拼」由两半决定——名字由文件布局定（opsx/<id>.md 目录命名空间→/opsx:<id>；opsx-<id>.md 文件名即命令→/opsx-<id>），前缀由工具定（绝大多数 /，Amazon Q 是 @）；技能拼写是另一套机制（Codex $、Kimi Code /skill:）。这段逻辑集中在 src/core/command-generation/invocation.ts，专防手写清单漂移（历史上 OpenCode、Cursor 都出过漂移 bug）。
设计得失 · 触发面的收敛

技能内容写的是「双拼写引用」：$openspec-propose (Codex) or /openspec-propose (other agents)，由 transformToCodexCompatibleSkillReferences 按目标工具改写（src/utils/command-references.ts）。一份技能文本同时伺候三种触发拼写，免去每工具维护副本。

4.4 入口三通道与防骚扰守卫（图 5）

值得注意的细节 · 自动触发守卫

每个 SKILL.md 内部都有分支：「Auto-selected」（模型自己选中）与「Explicit OpenSpec request」（用户点名）行为不同。当项目还没有 openspec/ 根时：自动选中 → 立刻放弃 OpenSpec、按普通请求作答、不提安装；用户点名 → 才询问是否 init。即触发机制不止「能不能被触发」，还带防骚扰守卫：OpenSpec 不允许技能在用户没点名时自作主张创建项目骨架。

证据：skills/openspec-propose/SKILL.md、skills/openspec-archive-change/SKILL.md（“Auto-selected: … Stop using OpenSpec … never create the root as a side effect”）。

6. 运行时契约与上下文/经验注入（图 8）

这张图回答：什么进入模型可见上下文、什么是 CLI 隐藏状态、经验怎么被注入。

机制先行：技能/命令本身不含业务逻辑，真正的规则在 CLI。代理的工作方式是「查指令 → 写工件 → 跑校验」，接口是 openspec instructions <artifact>|apply|archive --json（契约见 docs/agent-contract.md）。每次调用返回：工件模板与撰写指令（来自 schema）；依赖工件已有内容（工件图按 requires 推序）；context（必读必用）与 operationGuidance（择宜遵循）——来自 config.yaml，每次调用新鲜读取；任务进度、缺件/告警、下一步 instruction。

为什么值得这样切分 · 控制面 / 执行面

典型切分：CLI 是控制面（结构、依赖、合并、校验、留档），LLM 是执行面（撰写与编码）。validate 拦不住语义错误，但能拦「零 delta 却没声明 skip_specs」「工件缺失」「delta 格式错」这类结构错误；行为契约（如 guidance 冲突必须解释）写进 docs/agent-contract.md 供各家 harness 遵守，但明确承认不可被 CLI 强制。

常见疑问 · 提示词会被上传到 OpenSpec 服务器吗？

不会。OpenSpec 没有分析/组合提示词的服务端：openspec CLI 是纯本地程序，「代理 → openspec CLI」是本地 Bash 子进程调用，instructions 的富化输出只是本地文件拼装写 stdout。提示词真正去的地方是 harness 配置的 LLM 供应商 API，与 OpenSpec 无关。CLI 的外发面仅两类：① 匿名遥测（src/telemetry/index.ts → edge.openspec.dev，命令名/版本/surface/时间戳 + 随机匿名 UUID，OPENSPEC_TELEMETRY=0 可关）；② openspec feedback（用户逐项确认后经 gh issue create 或浏览器携反馈正文与版本/平台元数据发往 GitHub，src/commands/feedback.ts）。npm 版本检查、git 拉技能为无内容入向请求；store 共享由用户手动 git，CLI 不执行。

9. 经验能力盘点：核心有什么、缺什么

本节回答：核心 OpenSpec（上游 v2.1.0，不含本工作树扩展）到底有没有「经验总结」能力。结论：部分存在——有「经验注入」接口，无「经验自动总结」（缺口由 experience-loop 补，见 §11）。

9.1 核心有什么：经验注入通道（手动）

机制一：项目语境与操作建议（config.yaml）

解决什么问题：代理每轮上下文清零，项目惯例与历史教训需要持久载体。进什么：context（事实、惯例、约束，自由文本）与 operations.apply.guidance/operations.archive.guidance（字符串数组）。harness 做什么决定：每次 instructions 新鲜读出并区分权威级——context 是必用输入，guidance 是择宜建议（“适用且与内置工作流兼容才遵循”）。失败路径：冲突的 context 必须被报告；不适用的 guidance 不执行且必须解释原因。为什么重要：这是核心里唯一把「经验」当一等输入的接口——但它只读不写。

证据：src/core/project-config.ts（OperationInputs/loadOperationInputs）、docs/customization.md（“Operation guidance”）、docs/cli.md（“guidance is not followed and the reason is explained”）。

机制二：探索期洞察捕获（insight capture）

/opsx:explore 工作流内置「洞察 → 落点」映射表：新需求/需求变更 → spec、设计决策 → design.md、范围变化 → proposal.md、新工作 → tasks.md、假设被推翻 → 相关工件。捕获前必须向用户提议并获确认（“Don’t auto-capture”）。这是一次 change 内的经验固化，不跨 change。

证据：src/core/templates/workflows/explore.ts（捕获表与 “Offer to capture when decisions are made”）。

9.2 核心缺什么：自动回顾 / 教训回写

常见经验沉淀设施核心 OpenSpec说明（含 experience-loop 扩展是否补上）
变更后回顾（retro / lessons-learned 工件）核心无默认 schema 仅 proposal/specs/design/tasks 四工件。experience-loop 已补：retro 工件。
跨 change 经验库（自动积累/检索）核心无核心无 MEMORY/经验文件自动写入或注入。experience-loop 已补：openspec/experience/ + INDEX。
经验自动回写 config guidance核心无guidance 全靠人手；仓库 change 历史里的 “Lessons to carry forward” 是人在 proposal 里手写。
经验注入运行时有context + operationGuidance，按权威分级、每次新鲜读取、冲突须解释（见 9.1）。
过程洞察固化到工件半自动explore 洞察捕获表，需用户确认，仅限当前 change。
以 schema 扩展补 retro 工件可扩展schema 支持默认集之外的自定义工件与依赖图（测试注释以 “post-implementation retro” 为例）；社区 superpowers-bridge 已实现 evidence-first retrospective。experience-loop 即走此路。
产品反馈回路有但用途不同openspec feedback 是向 Fission 提交产品反馈（脱敏、需确认），不是项目经验沉淀。

10. 循环沉淀能力分析（图 11）

本节回答：核心有没有「循环沉淀」能力。结论：存在——但沉淀的是「行为真相」（specs），非「过程经验」（后者 experience-loop 补）。

10.1 沉淀主循环：delta 合并进主规格

OpenSpec 核心资产模型是「specs 是真相，changes 是提案」。每次循环：① explore（可选）→ propose 生成 change 工件（proposal、delta specs、design、tasks）；② apply 按 tasks 实现，verify 核对一致；③ sync/archive 把 delta specs 按 ADDED 追加 / MODIFIED 替换 / REMOVED 删除 / RENAMED 改名 合并进 openspec/specs/<capability>/spec.md（删掉最后一个需求即退役 capability，需 retire_capabilities: true）；④ change 整体移入 changes/archive/<日期>-<名称>/ 连同元数据与指纹长期留档。合并并非全自动：sync 是 agent 智能合并（skills/openspec-sync-specs），archive 由 CLI 机械规则兜底（src/core/specs-apply.ts）。因此每轮循环都在向 specs 沉淀：下一个 change 被要求先 openspec list --specs/show 查既有规格、复用 capability 路径。多轮后 specs 成为跨会话、跨代理的「行为记忆」。

边界要说清

沉淀的粒度是规格（系统该做什么），不是经验（我们学到什么）。一次失败尝试、一个坑、一条流程教训，除非被人工改写成 spec 需求或 config guidance，否则不留下——归档 change 里只有工件原文，无结构化复盘结论。核心也无机制把「上个 change 的教训」自动检索进下一个 change（能检索的只有 specs 与 config）。experience-loop 正是补这块（见 §11）。

10.2 沉淀的扩展面：schema 与 store

  • Schema 可加沉淀工件：自定义 schema（openspec/schemas/）能定义任意工件与依赖图。社区已补缺口——superpowers-bridge（evidence-first retrospective）、intent-driven（长期决策写成不可变、可 supersede 的 ADR，最接近「循环沉淀经验」）、ml-research（证据支撑的发现写成 Finding: 需求）。schema 工件机制本身支持 retro 类工件（docs/customization.md）。experience-loop 即用此扩展点。
  • Store（beta）跨项目沉淀：openspec store 把规划库放进独立 git 仓库，多项目/多机共享 specs、initiatives、work items（本仓库 openspec/initiatives/、openspec/work/、openspec/explorations/ 即其雏形）。这是「知识沉淀的空间扩展」，但同样是人写人读，CLI 不推送。

11. 经验闭环扩展（experience-loop）：补齐缺口

本节回答：本工作树新增的工程变更是什么、机制怎么闭环，如何补齐 §9/§10 指出的核心缺口。这是「治理面可插拔」不变量的完整示范——不改核心 CLI、不改生成的技能模板，仅用 schema + 规约 + 本地脚本实现。

机制先行：闭环四步——① retro 工件（schema 新增，requires: tasks，仅实现完成后创建）在 change 收尾复盘；② 经验人审后写入 openspec/experience/（单条一文件 + INDEX 逐字索引，supersede 链管理生命周期）；③ 下次 propose 按 capability/tags 检索注入，引用进「## 经验引用」，验证动作落为跟踪任务；④ experience-lint 执法/度量（归档前 --change 校验、CI 默认模式兜底、--report 出引用率/覆盖率指标）。失败路径：缺 retro 归档被 lint 拦（x-skip-retro 豁免须留 stub）；INDEX 与文件不一致、重复经验、supersede 链断/环均被 lint 打回。

工程落点

extensions/experience-loop/（扩展包规范源）→ 安装落位到 openspec/schemas/experience-loop/、openspec/experience/、openspec/experience/experience-lint.mjs；openspec/config.yaml 的 operations.archive.guidance 挂"归档前跑 lint"。本仓库已 dogfooding 就位。32 个专项测试 + 全量套件 6517 通过。

与核心缺口的对应

§9.2 表中标 “experience-loop 已补” 的三行——retro 工件、跨 change 经验库、检索注入——正是本扩展落地的能力；§10 图 11 的红色缺口（无自动 retro / 教训回写）由此填上。设计上的取舍：人审门（经验写入须人审，Don't auto-capture）与 lint 硬执法（唯一硬门，CI 未部署则无拦截）。

12. 结论清单与设计得失

问题结论一句话理由
Claude Code 如何触发双通道/opsx:<id> 命令（目录命名空间）+ .claude/skills 技能自动匹配。
Codex 如何触发单通道skills-only（.agents/skills），$openspec-<skill> 或 Skills 侧栏；无命令文件。
OpenCode 如何触发双通道/opsx-<id> 命令（文件名扁平）+ .opencode/skills 技能；正文注入 $ARGUMENTS。
自动触发有SKILL.md description 驱动模型侧自动选用，且带「未点名则退出」防骚扰守卫。
经验总结核心半自动核心有经验注入（context/guidance）与洞察捕获，无自动 retro/教训回写；experience-loop 补齐。
循环沉淀有delta → specs 规格沉淀 + 归档留档 + store 跨项目共享；核心沉淀物是规格非经验，experience-loop 补经验。

设计得失

  • 得：把「格式适配」与「规则引擎」彻底分离。30+ 工具差异压缩进 adapter + invocation 拼写推导；工作流规则只写一份（CLI + SKILL.md 模板）。跨工具迁移成本近似为零。
  • 得：触发面自带防御。allowed-tools 预授、auto-selected 守卫、指纹漂移检测、legacy 清理——命令文件的生命周期管理比多数同类工具完备。
  • 失：经验闭环缺最后一公里（已补）。核心会把「系统行为」沉淀成 specs，却不会把「工作过程教训」沉淀成任何东西。experience-loop 在 archive 工作流尾部加 retro 工件 + 经验库 + lint 补齐（§11）。
  • 失：行为契约不可执行。guidance“不遵循须解释”只是提示词约定，CLI 无法校验；experience-loop 的硬执法也仅 lint 一道门。依赖各家 harness 的模型自觉。

14. 术语表

术语含义（本项目语境下）
harness（宿主/工具壳）承载 LLM 代理的编码工具（Claude Code / Codex / OpenCode …），OpenSpec 通过向其目录写文件“接入”。
slash command（斜杠命令）AI 聊天框里的命令（如 /opsx:propose），本质是被工具加载的 prompt 模板文件，非终端程序。
skill / SKILL.md（技能）Agent Skills 标准的指令包，跨工具通用；模型按 name/description 自动选用或用户显式调用。
adapter（适配器）src/core/command-generation/adapters/ 每工具一个模块，决定命令文件路径与 frontmatter 格式。
invocation 拼写命令“怎么拼”：名字（opsx: 目录命名空间 vs opsx- 文件名扁平）+ 前缀（/、@、$）。
spec / capability（规格）openspec/specs/<capability>/spec.md：系统行为真相来源（Purpose + Requirements）。
change / delta spec（变更）openspec/changes/<name>/：一次提议变更的工件包；delta 用 ADDED/MODIFIED/REMOVED/RENAMED 头描述增量。
archive / sync specs（归档）把 delta 合并进主规格并把 change 移入 changes/archive/ 的动作，即“循环沉淀”发生时刻。
schema（工作流模式）定义工件集合与依赖图（默认 spec-driven：proposal→specs→design→tasks）；可自定义/社区分发，可加 retro 等工件。
context / operationGuidanceconfig.yaml 里的项目语境（必用）与操作建议（择宜遵循），每次运行新鲜注入的“人工经验”。
allowed-tools技能/命令 frontmatter 的权限预授字段，OpenSpec 写 Bash(openspec:*) 预批准 CLI 调用。
retro 工件（复盘）experience-loop 新增的收尾复盘工件（requires: tasks，仅实现完成后创建）；核心无，社区 schema 有。
经验库（experience/）单条一文件的经验生效区 + INDEX 逐字索引；propose 检索、retro 写入（人审后）。
x-skip-retro.openspec.yaml 豁免键（x- 前缀零告警）；豁免仍须留 stub skipped: x-skip-retro。
判定行retro 复查结案格式：- [经验 <id>] 判定: 生效|不生效|不适用 — 依据（lint 可解析）。
store（上下文仓库，beta）独立 git 化的规划库，多项目共享 specs/initiatives/work items；经验沉淀的跨项目载体（CLI 不推送）。
retrospective（复盘）变更结束后的结构化教训总结工件；核心无，社区 schema（superpowers-bridge）与 experience-loop 有。
循环沉淀本报告定义：多轮循环中知识被自动固化为持久资产并在下一轮生效的机制；核心对应 delta→specs，不含教训类经验。
控制面 / 执行面CLI 管结构、校验、合并、留档（控制面）；LLM 撰写与编码（执行面）。
指纹（fingerprint）/ drift生成文件的内容指纹，用于检测命令/技能文件被改动或版本漂移，openspec update 据此重生成。

16. 未知与需验证项

  • 各 harness 的自动触发灵敏度未实测：SKILL.md description 的语义匹配由各家模型决定，静态阅读无法证明三工具的自动选用率与误触发率。验证法：在三工具里各说一句“帮我做个暗色模式”，观察是否自动加载 openspec-propose。
  • guidance/retro 契约的遵守率：behavior contract（“不遵循须解释”、retro 条件化创建）是提示词约定，无法由 CLI 强制，依赖各家 harness 模型自觉——experience-loop 的硬执法只有 lint 一道门（CI 未部署或被绕过则无拦截）。
  • 经验库脱敏与检索：脱敏不机扫（密钥/个人信息靠 retro 规程 + 人审门）；检索无语义相似度，措辞差异大的重复条目绕过查重。
  • “智能合并” sync 的正确性：sync 路径由代理执行，靠 validate 结构校验兜底，语义层合并质量未被机器验证。
  • store beta 的成熟度：跨项目沉淀（initiatives/work items/evidence）在 docs/stores-beta/，API 与目录约定可能继续演进。
  • 本仓库是活跃 fork 还是上游镜像：remote 指向 Fission-AI/OpenSpec（经 gh-proxy），本地浅历史；openspec/、docs-lab/ 等自用目录表明项目在用 OpenSpec 管自身开发（dogfooding），其 changes/archive/ 里的 “Lessons to carry forward” 等文本属团队手工实践，非产品功能。
